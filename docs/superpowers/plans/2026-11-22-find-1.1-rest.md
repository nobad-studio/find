### Reference profiles, workloads, floors and outcomes (maintainer, 2026-11-22)

**Reference profiles are measuring points, not classification rules.**
- A real PC is never "put in a tier". Its budget comes from the spec's per-axis classes and its live usable
  resources (§4.1, §6.1).
- Each model's measured cost is checked against that budget.
- A PC with 8 cores and 8 GB is limited by its memory axis; it is not "High".

| Reference profile | Emulated on the reference PC as | Real example |
|---|---|---|
| `low` | 4 threads (affinity), Find's job memory capped as for an 8 GB PC, processor only | 4 cores / 8 threads, 8 GB, no usable GPU |
| `mid` | 8 threads, 16 GB, the built-in GPU allowed (Vulkan for talk; ONNX CPU build) | 6-8 cores, 16 GB, Iris Xe |
| `high` | all threads, 16 GB. Discrete-GPU rows are **estimated** until measured on such a PC | 8+ cores, 16-32 GB, GPU with ≥ 4 GB dedicated |

**Dedicated vs shared GPU memory.**
- Only dedicated VRAM counts as GPU capacity.
- On an integrated GPU (shared memory, e.g. Iris Xe), a model's GPU use is counted against the **system RAM
  budget**, once (spec A4). Its `vram_mb` is never added as separate capacity.
- `profile` and `suggest` take `dedicated_mb` and `shared_mb` from Task 2's facts and never treat `shared_mb` as
  VRAM.

**Two workloads, benchmarked and suggested separately** (they share infrastructure, not results):
- `photo_search`: finding photos by what's in them (embedding models: SigLIP base, SigLIP 2 variants);
- `photo_talk`: describing or answering about a single photo (VLMs: SmolVLM2, Qwen3-VL, on llama-cpu or
  llama-vulkan);
- and `text` (meaning search), as today.

**The floor is a guaranteed experience, not just quality.** A model meets the floor on a budget only if every
dimension holds:

| Dimension | `photo_search` | `photo_talk` |
|---|---|---|
| Search usefulness | ordinary visual queries (the evaluation's described/visual categories) score nDCG@10 ≥ 0.60 and recall@10 ≥ 0.70, from measurements.md (not tuned on held-out) | answers the benchmark's describe/ask/compare checks correctly (the existing real-model checks: 3/3) |
| Reliability | 0 crashes and 0 watchdog kills over a 500-photo indexing run plus 50 searches | 0 crashes and 0 hang-kills over 10 describe/ask/compare runs, incl. one cold load |
| Responsiveness | one photo search ≤ 300 ms (p95, warm); 10,000 photos indexed in ≤ 8 h at Gentle (≥ 0.35 photos/s) | first word ≤ 15 s (p95) and load ≤ 30 s on that runtime |
| Memory | worker peak ≤ the budget: 10% of installed RAM, within the WORKERS cap | worker peak ≤ 25% of installed RAM (shared GPU memory counted here) |
| Availability | a processor-only path exists (no dedicated GPU needed) | a processor-only path exists |
| Graceful degradation | on a smaller budget, a slower supported path (fewer threads, lighter equivalent variant) still meets Reliability and Memory; never a silent off | the same, or "Not now: …" with the reason; never a crash |

The numbers are the first proposal. They live in one table, `suggest.FLOORS`, so the maintainer can tune them
without code changes. The plan's tests use synthetic measured numbers.

**Three outcomes per workload, computed for this PC and the selected runtime:**
- **Suggested:** the best model that meets the floor on this PC's budget.
- **Available upgrade:** a stronger model that fits the budget (safety limits hold) but doesn't meet the suggested
  experience. For example, slower answers or more memory than the floor allows. The user can opt in. Before
  switching, Find shows this PC's **measured** figures for it: load time, answer or search time, peak memory, and
  index time if the vectors change. Never generic estimates.
- **Not recommended:** a model whose measured needs exceed the available budget, or whose measured performance is
  unsuitable (fails Reliability or Usefulness). It is listed with the reason. Choosing it needs an explicit "Use
  anyway" after the same measured-cost screen, and the safety limits still apply: it waits with its reason rather
  than running past them.

**No model names are assigned to profiles in code or docs until Task 4's benchmark has measured them against these
floors.** `suggest` reads only measured data. A model with no measurement for a budget is "not measured here"
(shown as such) and is never Suggested.

**Not in this plan** (later releases, per the spec's PR C/D):
- GPU batching (§6.2);
- the allocation-failure fallback chain and the learned reserve (§6.4, §7);
- the in-app "Test my PC" benchmark (PR D).

Suggestions use the measured rows from Task 4 until then.

## Review Focus

1. A PC that fits no photo model under the floors (very low RAM): there is no photo suggestion and a plain reason,
   never a model that will thrash. → Task 5 test `test_suggest_none_when_no_model_meets_floors`.
2. First run with no network or a failed download: the window still works with what is on disk. The popup offers
   to retry and never blocks searching. → Task 6 test `test_first_run_offer_survives_download_failure`.
3. A user picks a model above what's suggested, then RAM falls: the disclaimer stays and the model waits with a
   reason ("Not now: …"). It is never silently swapped. → Task 7 test
   `test_override_above_suggestion_waits_not_swaps`.
4. An upgrade that changes the photo vector tag while the user searches: the old vectors keep answering until the
   new ones are complete, and the two are never mixed in one list. → Task 10 test
   `test_search_during_rebuild_uses_one_identity_per_channel`.
5. Browser database locked or mid-write (`-wal` present): the copy is consistent or skipped with a note, and the
   browser is never touched. → Task 12 test `test_locked_history_is_copied_or_retried_never_killed`.
